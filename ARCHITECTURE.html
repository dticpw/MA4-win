读图时会遇到的几个词

SSE：后台持续推给网页的一条事件流

浏览器用 EventSource 发起 HTTP GET，后台保持响应连接，用 text/event-stream 连续写入事件。它是服务端到浏览器的单向推送；用户发消息仍走单独的 POST。Hub 为事件编号并保留最近 500 条；序号过旧时发 resync，网页重取状态。代码有重连与补状态路径，但这里不承诺事件永不丢失，也未实测断线恢复。

WebSocket 与 JSON-RPC：连接和消息格式

WebSocket 是双向、持续的消息连接；本项目在 Linux 使用 Unix socket，在 Windows 使用 Codex proxy 字节管道，也支持显式本机 TCP，连接本机 Codex，不是浏览器直连模型。JSON-RPC 是连接里面的“调用约定”：method 是方法名，params 是参数，id 将请求与响应配对；通知没有请求 id。两者分别解决“怎样传”和“传的是什么”。

thread / turn / item：会话、回合、条目

thread 是可继续对话的一条 Codex 会话；turn 是一轮运行，从开始到完成，可经历多个模型调用与工具调用；item 是这一轮里的消息、命令或文件改动条目。任务另外有 task ID。图中的 Python threading.Thread 是进程内的执行线程，不是 AI 会话，也不意味着一个会话独占一个 Python 线程。

事件驱动与轮询：两者同时存在

文字增量和完成通知到来后触发处理；中控不需要让模型循环问进度。但 Hub 默认每 3 秒刷新会话列表；Controllers 的队列空闲等待最多 0.5 秒，处理后调用 tick，并每 15 秒核对相关回合。侧栏也定时查询。SSE 的 20 秒保活是维持连接，不是每 20 秒才显示一批文字。

request_id 与 RPC id：管不同层的关联

网页为发送生成 request_id，Hub 用内存中的 sent 缓存最近受理结果，并将它作为 clientUserMessageId 传入 Codex。通信层另分配 RPC id 来匹配请求/响应；它们不等于 thread ID 或 turn ID。中控还会把发送标记写进任务状态与消息，以便恢复核对。普通发送缓存不持久化，不能由此宣称跨重启“恰好一次”。

pending / outbox：待回传内容与待确认发送

pending 保存执行者已经结束但尚未交给中控的报告；outbox 保存一项已经准备发送、结果仍待确认的操作。它们在当前任务状态文件中，作用不同。报告送达无需等待所有目录停止写入；中控只能对稳定的文件作验收。暂停、断线、恢复核对或硬预算限制都可能让报告继续保留。

页面里的“中控会话”和代码里的 Controllers 各自承担不同职责。

AI · 中控会话

对目标与验收负责

收到消息后运行一轮模型，理解要求、分配工作，独立检查实际产物。

  • 决定先做什么、派给谁。
  • 比较实际成果与完整目标。
  • 决定返工、暂停、交接或结束。

任务判断依赖模型能力与实际证据。

程序 · controllers.py

管理状态与推进条件

接收事件并按规则处理，保存任务关系、预算、队列和结果。

  • 允许时启动执行会话，协调写入。
  • 接收完成通知，把报告交回中控。
  • 检查时限与用量，记录结束数字。

运行在原有服务里，不需要模型代为轮询。

一轮回答结束后，任务仍然可以继续。中控派工后结束当前回合，程序等执行结果到达，再发起中控的下一轮。模型不用持续说“我再看看进度”。这叫事件驱动：完成通知、用量变化和用户操作会触发后续处理；程序仍有定时预算检查与每 15 秒的相关回合核对。

Controllers 有自己的串行事件处理线程。WebSocket 读取线程只投递事件，不在回调里同步等待另一条 RPC，避免互相卡住。这里的“程序线程”和 Codex 的“会话 thread”是两个概念。

从“打算派工”到真正发起任务
补充

从“打算派工”到真正发起任务

创建中控会话时，MA4 注册三个动态工具。模型发起调用后，本地程序执行相应动作并返回结果。

TOOL / 01

ma4_dispatch

创建或复用执行会话，登记具体任务、读写权限和项目相对写入范围，加入队列。

TOOL / 02

ma4_control

查看任务、交还等待、暂停、结束或交接。结束时提交达标/未达标结论与证据。

TOOL / 03

ma4_artifacts

检查临时材料，登记保留理由，清理明确属于本任务且已无依赖的精确路径。

中控模型调用工具→Codexitem/tool/call→通信客户端appserver.py→Hub 转接on_request→运行控制tool_call

模型在聊天中写“我准备派工”，只是文字；调用 ma4_dispatch 才会让程序登记和安排执行。工具请求会带上会话身份，程序只接受本任务当前中控的调用。返回结果沿原连接送回模型。

动态工具通过 thread/start 的 dynamicTools 注册。OpenAI 官方说明将此接口标为 experimental；升级 Codex 时需要核对协议兼容性。

跟着一次派工，走完这条链路
补充

跟着一次派工，走完这条链路

以“先做一段角色代表动作样板”为例。点击步骤只切换说明，不会连接 MA4 或启动任务。通信细节沿用上面的主链。

你目标、授权与关键确认
MA4 程序控制运行与保存状态
中控会话判断、派工与验收
执行会话完成具体工作
项目文件与实际成果源码、素材、运行证据
  1. 01 / 创建

    先填项目、名称和时限

    时限由你填写，单位 min，经费默认不限。初步想法可留空；填写后会作为第一条讨论消息发给中控。MA4 保存任务和预算，此时不启动自动执行。

    创建空白中控不调用模型；填写想法或开始聊天会产生模型消耗，执行时限尚未开始。

  2. 02 / 配置

    程序建立中控会话

    通过 Hub 新建 Codex 会话，配置中控角色说明、完全访问与从不审批权限，以及三个动态工具，并把会话 ID 关联到任务。

    new_host → Hub.new_thread → thread/start
    这是带有专门配置的 Codex 会话，仍由原有后台运行。

  3. 03 / 讨论与启动

    商讨草案，确认后再执行

    你直接与中控讨论，由它整理目标、范围和验收草案。页面对照显示当前正式目标与新草案；你确认完整目标和预算并点击启动后，程序才开启自动推进。

    草案和正式目标分开保存，普通讨论不恢复任务。创建时填写的启动后时长在首次启动时换算为固定截止时间；暂停、续接、交接和重启不顺延截止时间。消息区区分用户、自动通知与执行者回报，附带的任务信息可展开查看。

  4. 04 / 决策

    中控安排代表动作样板

    中控判断优先级后调用 ma4_dispatch，提供具体要求、读写权限和写入范围。程序返回“已排队”。

    执行者不会自动拥有中控的完整上下文。它收到的是这次明确写出的任务，以及权限和材料说明。

  5. 05 / 排队

    中控结束本轮，程序接着管理

    中控结束当前回合。程序检查预算、项目写入冲突和运行状态，条件允许后再启动执行者。

    等待由程序处理，模型不需要循环查询。省略 write_scope 时继承已确认目录的授权范围；显式空数组代表整个目录，须已有相应授权。明确不重叠的范围可以并行。

  6. 06 / 执行入口

    具体任务发给执行会话

    程序经原有消息链路发送指令，附上读写范围、任务临时目录和交付要求。执行者开始一轮工作。

    launch → Hub.send_raw → turn/start
    同一个执行会话可以在后续轮次继续使用。

  7. 07 / 制作

    执行者完成修改与验证

    素材和源码直接进入所属项目，临时材料放在任务目录。执行者核对结果，最后报告成果路径、验证、失败项及材料去向。

    主要制作和修改交给执行者。中控具备完全访问能力，但聚焦统筹和独立检查；必要的少量辅助修改需避开执行者正在修改的文件。

  8. 08 / 事件

    Codex 通知这一轮结束

    完成事件经通信客户端到 Hub，再送入 Controllers 的事件队列。程序提取执行者最终报告，记录回合状态和收到的用量。

    若事件没有完整回答，按需读取对应历史。长报告取前 2,000 字和后 1,000 字，另列失败信息与会话/轮次身份。

  9. 09 / 回传

    报告交回空闲的中控

    中控忙碌时报告先保存在 pending；空闲且任务状态、预算允许时，每批最多 8 份交给中控，并再次附上当前完整目标、预算和状态，开始新的验收回合。

    发送确认后才清除对应报告；发送不明时保留标记并核对，不盲重发。报告附带当前写入路径快照；其他执行者写入不阻挡报告送达，但相关文件仍需暂缓验收。完整解释仍可回原会话读取。

  10. 10 / 验收

    中控检查真实效果

    对照完整目标读取实际素材、运行证据和必要的实机画面。执行者说“完成了”只是报告，不能自动算目标达标。

    发现问题可以继续派工。代表样板通过也只是阶段成果；若任务要求用户确认方向，中控须在扩大制作前暂停等待确认。

  11. 11 / 结论

    结束需要明确工具动作

    可以结束时，中控调用 ma4_control 的 finish，提交 met 或 unmet、结论和实际证据。程序检查是否还有未完成的执行工作或未回传结果。

    单轮结束、会话空闲、聊天中说“完成”，都不自动等于整个目标通过。

  12. 12 / 收尾

    数字由程序继续补齐

    结束记录保存结论和证据。迟到的收尾用量继续更新，网页通过原有事件流看到统计，无需为补数字再开一次模型回合。

    预算可能有在途消耗，不能精确截断。必要成果留项目，临时材料按已核实的归属和依赖收尾。

01 / 12

原生会话与对话

PROJECT

实际工作成果

源码、素材、游戏文件与必要证据直接保存在所属项目。临时材料按任务归属收尾。

项目正式文件 / 任务临时目录

MA4 原有的偏好文件仍保存置顶与已读状态，额度仍使用原有缓存。新增任务状态文件用原子替换保存当前记录，不复制完整原生对话，也不逐轮复制项目。

重连或重启后，程序把已保存的任务关系与 Codex 中的实际回合核对。发送结果不明时保留待核对状态，暂停自动推进；不会猜测成功或盲目重发。浏览器只是操作入口，关闭页面后，服务正常运行的中控任务仍可继续。

BOUNDARY / 01

流程条件由程序检查

预算、写入排队、结果关联、结束工具参数都可以按规则处理。图像是否好看、成果是否满足目标，仍需要模型与人的实际判断。

BOUNDARY / 02

写入范围属于协作约定

同一任务可确认多个工作目录，共用目标和预算；每个执行者绑定实际目录，write_scope 相对此目录。程序跨所有任务检查实际路径冲突。目录授权不是操作系统沙箱，也不能拦截其他终端的写入。

BOUNDARY / 03

计量遵守观测边界

缓存输入单列；并行回合用时之和不等于任务历时。通知可能迟到，恢复时缺失的数据明确标为未归属或约值。
